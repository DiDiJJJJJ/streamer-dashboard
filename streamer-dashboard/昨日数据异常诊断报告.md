# 昨日数据异常诊断报告

> 现象：主播数据页「昨日」总流水与 B站 后台实际值不符，但「本月」总流水正确。
> 诊断日期：2026-08-10｜数据基准：`server/data/latest.json`（即前端 `./streamer_data.json`）

---

## 1. 结论速览

| 项目 | 结论 |
|------|------|
| 页面计算逻辑是否有 bug | **无**。用「仅单日且日期=昨日」的修正算法复算，结果与页面完全一致（差值 ¥0.00）。 |
| 昨日数字为何偏低 | 昨日(8/9)记录在数据文件中是 **13:07 的早盘快照**，B站 礼物/大航海按日汇总存在 **T+N 延迟结算**，延迟部分尚未入账。 |
| 与后台的差额 | 页面 ¥16738.20 vs 后台 ¥17044.4，差约 **¥306**（即 T+N 延迟结算缺口）。 |
| 本月为何"正确" | 本月内更早的日期是在各自"次日 13:00"抓取的，到那时其 T+N 大多已结算，记录接近最终值；唯独最新的"昨日"缺口最明显。 |
| 修复方式 | 已由 `cronYesterdayFinal`（每日 **20:00 收盘补抓**）覆盖为最终结算；亦可手动触发补抓即时校正。 |

**一句话根因**：昨日总流水"算得对、但取的是早盘快照"，并非计算或接口同步 bug，而是**数据新鲜度（抓取时机）**问题——早盘快照早于 B站 延迟结算入账。

---

## 2. 定位过程

### 2.1 复核前端聚合逻辑
主播数据页聚合入口在 `src/components/Dashboard.jsx`：

- `aggregateByRoom(records, dateRange)`：按 `房间号` 聚合，仅对落在所选区间的记录求和 `总流水（元）`。
- 区间判定 `inDateRange` → `parseStatEndDate(r['统计时间'])`：取 `统计时间` 字符串里**最后一个 `YYYY-MM-DD`**，再用 `isWithinInterval` 判断是否属于"昨日"区间。

"昨日"区间由 `QuickDateFilter` 计算：`startOfDay(subDays(today,1)) ~ endOfDay(subDays(today,1))`（即 8/9 00:00 ~ 8/9 23:59:59）。逻辑自洽，无边界错误。

### 2.2 实证复算（脚本 `_diag_yesterday.mjs`）
对 `latest.json`（10684 条）做与页面**完全相同**的聚合，并额外用"仅单日且日期=昨日"算法交叉验证：

```
统计时间 格式分布（节选）：
  RANGE(2026-08-09~2026-08-09): 1070   ← 起止同日的单日快照
  RANGE(2026-08-08~2026-08-08): 1070
  ...（8/1 ~ 8/10 每日各约 1070 条）
单日记录: 10684，区间记录: 0            ← 不存在跨多日的"区间记录"

Dashboard 当前逻辑聚合：
  昨日(Aug9) 总流水 = ¥16738.20   命中 1070 条
  本月(Aug)  总流水 = ¥188247.60  命中 10684 条

修正后昨日（仅单日记录且日期=2026-08-09）：
  昨日(单日) 总流水 = ¥16738.20   记录 1070 条
  差值(当前-修正) = ¥0.00          ← 计算逻辑零偏差
```

结论：**页面数字忠实地反映了数据文件**，计算链路无误。任何"少算"都来自数据本身，而非聚合。

### 2.3 追踪数据来源
数据写入链路（`server/fetcher.js`）：

1. `fetchData('yesterday')` 导出 B站"昨日"页 → 标记 `统计时间 = "2026-08-09 ~ 2026-08-09"` → 写入 `yesterday.json` → 经 `mergeRecords`（房间号+日期去重）并入 `latest.json` → `syncToPublicDataset()` 同步到 `public/streamer-dashboard_data.json` 与 `dist`。
2. 定时任务（`server/index.js`）：
   - `cronYesterday` = `0 13 * * *`：**13:00 早盘快照**。
   - `cronYesterdayFinal` = `0 20 * * *`：**20:00 收盘补抓**，覆盖昨日为最终结算。
3. 文件时间戳印证：`yesterday.json` 修改于 **13:07**，`latest.json` 修改于 18:00（由"今日"每 20 分刷新驱动，未触碰昨日）。**当前 18:05，20:00 的收盘补抓尚未执行**，故昨日仍为 13:07 早盘值。

### 2.4 已排除的其他嫌疑
| 嫌疑 | 排查结果 |
|------|----------|
| 分页缺失导致少算 | 否。聚合在全部记录上完成，分页仅影响展示。 |
| 去重/过滤逻辑丢数 | 否。`mergeRecords` 以 房间号+日期 去重，诊断脚本统计 0 条重复房间号。 |
| 字段口径不一致 | 否。页面与后台均用 `总流水（元）` 同一口径。 |
| 汇率/单位换算 | 不涉及（均为人民币元）。 |
| 失败重试丢数 | 否。`yesterday.json` 一次成功写入，无部分失败。 |

---

## 3. 根因确认：T+N 延迟结算

B站 主播数据按日汇总存在 **T+N 延迟结算**（礼物、大航海等收入在发生后第 N 日才入账到"昨日"汇总）。13:00 抓取时，当日的延迟结算尚未完成，故快照偏低于后台最终值；20:00 再次抓取时大部分已结算，数值接近后台。

- 8/9 后台最终值 ≈ **¥17044.4**，13:07 快照 = **¥16738.20**，缺口 ≈ **¥306**。
- 本月内更早的日期（8/1~8/8）是在其"次日 13:00"抓取，到那时其 T+N 基本已结算，因此本月总额与后台吻合（这也是"本月正确"的原因）。

---

## 4. 修复方案

### 4.1 长期（已落地）
- `cronYesterdayFinal`（`0 20 * * *`）已在 `server/config.js` 与 `server/index.js` 实现：每日 20:00 重新抓取"昨日"并覆盖 `latest.json`，使昨日最终与后台一致。
- 该配置项已加入 `POST /api/config` 白名单，支持**动态调整**抓取时机（如改为 `0 21 * * *`）。

### 4.2 即时校正
- 在「数据自动同步」页点击 **【抓取昨日】**（即 `POST /api/fetch?type=yesterday`，需管理员口令）→ 立即用最新结算覆盖昨日记录。建议在 **约 20:00 之后**操作，此时 B站 延迟结算已基本完成，刷新后与后台一致。

### 4.3 透明度（本次已加）
- 主播数据页新增 **「昨日数据快照状态」徽标**：拉取 `/api/status` 的 `lastYesterday`，显示"昨日更新 HH:mm · 早盘快照/已结算"，并附带说明：早盘快照可能略低于后台，20:00 收盘补抓后更新为最终值。避免运营误判为系统 bug。
