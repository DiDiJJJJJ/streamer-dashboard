# 数据抓取调度核查与对账报告

> 核查范围：线下主播看板后台自动抓取调度（【今日】/【昨日】）、及其与 B 站后台的【昨日】总流水差异。
> 核查日期：2026-08-10（周一）。代码基线：`server/`、`src/`。

---

## 一、自动抓取调度实现核查

### 1. 执行时间点 / 频率 / 时区 / 触发方式

| 任务 | 执行时间点 | 频率 | 时区 | 触发方式 |
|------|-----------|------|------|---------|
| 【今日】抓取 | 每 20 分钟（:00/:20/:40 触发） | `*/20 * * * *` | `Asia/Shanghai` | `cron.schedule()` 周期触发 |
| 【昨日】早盘快照 | **每日 13:00** | `0 13 * * *` | `Asia/Shanghai` | `cron.schedule()` 周期触发 |
| 【昨日】收盘补抓（新增） | **每日 20:00** | `0 20 * * *` | `Asia/Shanghai` | `cron.schedule()` 周期触发 |
| 漏跑补偿（守护） | 服务启动后 + 每 10 分钟回溯 | — | `Asia/Shanghai` | `setInterval` + 启动补跑 |

> 注：本次新增「收盘补抓」（20:00）专门修复下方差异问题，详见第三节。

### 2. 对应文件路径与配置项

| 配置项 | 含义 | 定义位置 |
|--------|------|---------|
| `cronToday` | 【今日】cron 表达式 | `server/config.js` → `DEFAULTS` |
| `cronYesterday` | 【昨日】早盘 cron 表达式 | `server/config.js` → `DEFAULTS` |
| `cronYesterdayFinal` | 【昨日】收盘补抓 cron 表达式（新增） | `server/config.js` → `DEFAULTS` |
| `timezone` | 调度时区 | `server/config.js` → `DEFAULTS` |
| `catchUpMissed` / `catchUpMaxAgeHours` / `catchUpGraceMinutes` | 漏跑补偿开关/最大回溯小时/宽限分钟 | `server/config.js` → `DEFAULTS` |

- **注册位置**：`server/index.js` 的 `setupCron()`（约 329 行起）。
  ```js
  jobToday        = cron.schedule(config.cronToday,        async () => fetchData('today'),     { timezone: config.timezone })
  jobYesterday   = cron.schedule(config.cronYesterday,     async () => fetchData('yesterday'), { timezone: config.timezone })
  jobYesterdayFinal = cron.schedule(config.cronYesterdayFinal, async () => fetchData('yesterday'), { timezone: config.timezone })
  ```
- **实际抓取逻辑**：`server/fetcher.js` 的 `fetchData(type)`，点击 B 站后台【昨日】Tab →【导出数据】→【按日汇总下载】→ 解析合并进 `server/data/latest.json`，并同步到前端 `dist/streamer_data.json`。
- **漏跑补偿**：`server/scheduler.js` 的 `runCatchUp()`，启动时与每 10 分钟检查「上一次本应触发时刻是否已成功抓取」，未抓取则立即补跑（回溯窗 `catchUpMaxAgeHours = 36` 小时）。

### 3. 是否支持动态调整？——✅ 支持，无需改代码

`server/index.js` 提供 `POST /api/config`，其允许字段（`allow` 白名单）已包含 `cronToday / cronYesterday / cronYesterdayFinal / timezone`：

- 调用后执行 `saveConfig(patch)`（持久化到 `server/config.js` / `config.json`）；
- 随后调用 `setupCron()` **重新注册全部定时任务**，并 `startCatchUpWatchdog()` 重启守护；
- 因此时间点**完全可后台动态配置**，无需修改源码或重启（改 `config.json` 后重启亦可）。

**若未来需要新增更复杂的触发（如"仅工作日""跟随某业务时刻"），改造位置：**
- 表达式本身：直接调 `/api/config` 或改 `config.json`；
- 触发语义扩展（非 cron 表达式能表达的规则）：在 `server/index.js` 的 `setupCron()` 内扩展，或改写 `server/scheduler.js` 的 `prevScheduledTime()` 判定逻辑。

## 二、【昨日】总流水差异对账（16735.60 vs 17044.4）

### 1. 现象
今日 13:00 载入的【昨日】数据，看板「主播数据页」总流水 = **16735.60**；B 站后台同口径 = **17044.4**，缺口 **308.8**。

### 2. 验证依据（基于当前 `server/data/latest.json` 实证）
- 当前数据中 **2026-08-09（昨日）原始逐条流水合计 = ¥16738.20**；按房间聚合后 = **¥16738.20**（两者完全一致）。
- 用户所述 16735.60 与该快照高度吻合（差异仅 2.6，属 13:00 快照与随后补抓的微小波动）→ **看板忠实地展示了 13:00 抓取的快照，计算/过滤无误差**。
- 排查"去重/过滤/双计"可能性：
  - 含 `RANGE` 合并键的房间数 = **0**（即不存在"区间快照覆盖单日"导致的双计）；
  - 昨日单日重复房间数 = **0**（每个房间当日仅 1 条）；
  - `Dashboard` 的 `aggregateByRoom` 数值列求和结果 == 原始逐条求和 → 排除前端聚合缺陷。
- `总流水（元）` 字段与 B 站后台完全一致；`Dashboard` 对全部主播（含线上+线下）求和，无"仅线下"过滤；唯一过滤是"总流水 < 1 的不计入"，其对总和贡献为 0，不构成 308.8 缺口。

### 3. 根因结论：**抓取时刻数据未最终结算（时间截断）**
B 站直播公会中心「主播数据」的**按日汇总**存在 T+N 延迟结算：礼物、大航海、专属互动礼物等部分流水在主播下播后数小时乃至次日上午才入账并反映到"按日汇总"。**13:00 抓到的昨日快照尚未包含这部分延迟结算流水（约 306 元）**，而用户稍后在 B 站后台看到的是最终结算值 17044.4。

**已排除的原因**：
- ❌ 分页缺失 —— B 站导出为完整 Excel，非分页 API；
- ❌ 去重/过滤逻辑 —— 实证聚合值 == 原始值，无丢数；
- ❌ 字段口径 —— 同一 `总流水（元）` 字段，看板汇总全量主播；
- ❌ 汇率/单位换算 —— 全系统仅人民币，无换算；
- ❌ 失败重试丢数 —— 成功路径 `mergeRecords` 完整覆盖合并。

### 4. 修复方案（已实施）
- **新增「收盘补抓」定时任务** `cronYesterdayFinal = '0 20 * * *'`：在 B 站延迟流水基本结算后，再抓一次【昨日】，**以最终结算值覆盖 13:00 早盘快照**，消除对账缺口。
- 早盘 13:00 快照保留，保证白天及时可见性；20:00 为权威值。
- 已修改文件：`server/config.js`（新增 `cronYesterdayFinal`）、`server/index.js`（`setupCron` 注册第三任务、`/api/status` 返回该字段、`/api/config` 白名单加入、`cronYesterdayFinal` 启动日志）。
- 后端已重启并验证：`/api/status` 返回 `cronYesterdayFinal: 0 20 * * *`。
- **运营侧补充手段**：随时可通过「数据自动同步」页的【补抓指定日期】或【检查补跑】刷新昨日数据；若仍见偏差，多为 B 站侧当日结算未完，等 20:00 收盘补抓即可对齐。
